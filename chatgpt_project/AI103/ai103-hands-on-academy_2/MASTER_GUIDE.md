# Master execution guide and project glossary

Reviewed edition 1.2 · 23 October 2026

This is your navigation document. Execute one notebook at a time, read its short Python implementation,
and keep the matching RUNBOOK open. Shared modules, tests and deployment files are **not** extra lessons
to run in sequence. Every code file now begins with Purpose, Learn and Run notes.

## 1. Prepare your first session

1. Extract the ZIP and keep the single `ai103-hands-on-academy` folder intact.
2. Read [START_HERE](START_HERE.md), [beginner guide](docs/BEGINNER_GUIDE.md), then [Databricks setup](docs/setup/DATABRICKS.md).
3. Create/select Databricks compute with Python 3.11+ and a writable Unity Catalog volume using that setup guide.
   Compute can cost money even when a lesson uses no Azure AI service.
4. Upload the complete ZIP to the volume. Import [00_BOOTSTRAP](databricks/00_BOOTSTRAP.py) as a Python **source notebook** into Workspace.
   Set `zip_path` to the uploaded ZIP and `output_root` to `/Volumes/<catalog>/<schema>/<volume>/ai103-output` with your actual names.
5. Run bootstrap. Copy its printed `project_root` and `output_root`. It extracts to a temporary driver folder; rerun after compute restarts.
   On upgrade upload this new ZIP and rerun bootstrap; it replaces the temporary course copy. Keep your experiments in separate workspace notebooks.
6. Import the lab 00 notebook below. Set those two widgets. Leave `live=false`, `variant=default`, `config_json={}`, `input_file` blank.
7. Run its cells top to bottom. Read the printed evidence directory and `run_status.json` (`status=completed`).
   Then inspect the lesson's own output and explain it before moving forward.

## 2. Repeat this process for each lesson

1. Open the RUNBOOK in the table. Read prerequisites, secret names, setup links, expected output and failure guidance.
2. Run offline first. This uses local rules or labeled fixtures; it does not demonstrate successful Azure calls or model quality.
3. Open the implementation linked under **Read code**. Follow its imports only as needed. `opts.live` selects the real service branch;
   `args()` receives the widget values; `save()` writes evidence. Do not paste credentials into Python or widgets.
4. For a live exercise, complete its Azure Portal setup and any explicitly linked Foundry/Databricks setup.
   Create exactly the secrets listed in its RUNBOOK; the notebook loads them through `secret_scope`.
5. Set `live=true` only where supported. Choose the listed variant, upload media when required, and set non-secret `config_json` values.
   Run the package-install cell, restart Python once, then run the final execution cell. A compute restart requires bootstrap again.
6. Inspect `environment.json`, `run_status.json`, and the lesson output in the newly printed folder.
   `completed` means the program finished; compare its content against the RUNBOOK checkpoint too.
7. Change one safe input, predict the outcome, rerun, and test one expected denial/failure. Record evidence in [PROGRESS.csv](PROGRESS.csv).
   Stop compute and clean up resources as instructed when finished.

Use [configuration](docs/CONFIGURATION.md) for widget values, [troubleshooting](docs/TROUBLESHOOTING.md) for errors,
and [Azure execution](azure_execution/README.md) for work that belongs outside Databricks.
Do not run all files or enable every live variant in a single session.

Follow labs 00–32 in order. Extensions are placed immediately after their parent lesson so prerequisites stay visible.
Capstones come last and combine earlier skills. For the first two days, aim for 00–05 and 08–12 if time permits;
return to 06–07 and the remaining sequence afterward. Full cloud completion takes more than a two-day sprint.

**Mode key:** Azure = offline first, then a configured live Azure branch; local = keep `live=false`;
portal = keep notebook `live=false` and complete its separate Azure exercise; protocol = `live=true` starts the real local MCP protocol after package install.

## 4. Important execution dependencies

| Before executing | Complete or choose |
|---|---|
| First model call (02) | Lab 01 secret setup and Foundry model deployments. Deployment names are not model family names. |
| Search queries (09), live RAG (11), live retrieval evaluation, FAQ capstone | Run lab 09 `live=true, variant=ingest` first with the same `SEARCH_INDEX`; then test keyword, vector, hybrid. Semantic requires enabled semantic ranking. |

| Managed agent (16) | Foundry project endpoint, identity roles and an available model; model endpoint and project endpoint differ. |

| MCP (21) | Offline demonstrates expected shape. Live starts a real stdio subprocess and requires the MCP package. Use the documented VM fallback if compute disallows subprocesses. |
| Evaluation (23) / image generation (28) | These adapters require `MODEL_AUTH=key`; they reject Entra configuration. |
| Custom document extraction (25) | Train/deploy a custom model first, then set `DOCUMENT_MODEL_ID` in `config_json`. |
| Agentic analyzer preview extension | Follow its own RUNBOOK for preview API, model mapping, supported input and quota. GA Content Understanding setup alone is insufficient. |
| Speech (27) | Default live run can synthesize a sample WAV. Native speech libraries may require the separate VM route. |
| Video (29) | A paid new job is created by default. For `resume` or `remix`, set `VIDEO_ID` from prior evidence. |
| Fabric (30) | Choose `fabric` for live; requires Fabric SQL setup, authorized connection and ODBC Driver 18. Default uses synthetic data. |
| Receipt capstone | `approve` is an offline fixture only; do not use it to approve real receipts. |
| Contact-center speech capstone | Finish text flow first; `speech` live needs a short WAV in `input_file` and Speech secrets in addition to text/RAG secrets. |
| Enterprise capstone `fabric` | Complete lab 30 Fabric live and lab 09 ingestion; add the Fabric connection secret. |

## 8. Configuration, evidence and document glossary

| File/folder | Meaning and how to use it |
|---|---|
| `config/execution.json` | Launcher catalog: target Python file, dependency file, required secrets, allowed variants and execution mode. Read to understand dispatch; do not enter secret values. |
| `.env.example` | Optional terminal/VM configuration template. Never put a populated `.env` in the ZIP or repository. Databricks uses secret scopes instead. |
| `requirements/*.txt` | Per-topic dependency groups; the live notebook installs its own group. Package ranges are not a verified lockfile. |
| `pyproject.toml` | Python package name/version and build metadata for optional installation and CI. |
| `data/` | Synthetic inputs and explicitly labeled offline fixtures. A fixture is a saved example, not a current service result. |
| `evals/` | Small evaluation datasets. Add representative held-out and adversarial examples before using a production gate. |
| `docs/setup/` | Resource setup, identities, model deployments, networking and prerequisite walkthroughs. |
| Lesson `README.md`, `RUNBOOK.md`, exercises/answers | Concept explanation, exact execution, experiments and self-checks. Read RUNBOOK before live execution. |
| `PROGRESS.csv` | Your record of explained, local verified, Azure verified and failure-tested progress. |
| `review_evidence/` | Results produced during this review. Historical evidence is labeled; it does not represent your subscription. |

## 9. Concepts in plain language

| Term | Meaning | First place to study |
|---|---|---|
| LLM / deployment | A model generates output; an Azure deployment is the named serving configuration your client calls. | 02 |
| Secret / identity / RBAC | A secret is sensitive credential material; identity says who calls; roles determine allowed actions. | 01 |
| Guardrail | A control that screens or limits behavior. It reduces specific risks and needs failure tests. | 04–05 |
| Prompt injection | Untrusted content attempts to change application instructions or trigger unauthorized actions. | 05, 24 |
| Structured output | A schema-constrained response; valid structure is not proof the content is true. | 03 |
| Token / context window | Model text units and the bounded input/output capacity; character counts are only an approximation. | 02, 15 |
| Embedding / vector | A numerical representation used for similarity, not an exact lookup or truth measure. | 08 |
| Chunk / overlap | A piece of source text and repeated neighboring context used during indexing. | 08 |
| Keyword / vector / hybrid / semantic | Lexical matching, embedding similarity, a combination, and semantic reranking. | 09 |
| RAG / grounding / provenance | Retrieve evidence, use it to answer, and retain where it came from. | 11 |
| Tool / function calling | A model proposes a named operation; application code validates and decides whether to run it. | 12 |
| Agent / orchestration | A bounded model/tool loop and the code coordinating its steps or multiple participants. | 12, 16–19 |
| Tenant / principal | An isolation boundary and the trusted identity/role used to enforce that boundary. | 13 |
| Idempotency / retry | Repeated submission has one effect; retries repeat attempts only when safe and bounded. | 14 |
| Cache / TTL | Reused results and their expiration interval; keys must retain identity and policy context. | 14 |
| Memory / summary | Stored conversation state and a compressed representation that can omit important details. | 15 |
| MCP | A tool-discovery/invocation protocol; it does not replace authorization. | 21 |
| Trace / span | A recorded execution and timed sub-operations, with sensitive data excluded. | 22 |
| Evaluation / regression gate | Measure outputs against expected behavior and stop changes that fail defined criteria. | 23 |
| OCR / layout / analyzer | Recognized text, document structure, and configured content extraction behavior. | 25–26 |
| STT / TTS | Speech-to-text and text-to-speech. | 27 |
| Async job / polling | A service operation continues remotely; the client checks its status using the returned ID. | 29 |
